# 리팩터링 계획

이 문서는 기존 코드를 어떤 순서로 나눌지 정리한다. 목표는 한 번에 크게 갈아엎는 것이 아니라, 기능을 추가할 때 필요한 부분부터 작게 분리하는 것이다.

## 리팩터링 원칙

- 동작 변경과 파일 이동을 한 커밋에 크게 섞지 않는다.
- 기능 추가 전에 관련 로직만 먼저 분리한다.
- 기존 앱이 계속 실행되는 상태를 유지한다.
- 분리 후에는 수동 테스트 결과를 `docs/testing/test_result.md`에 남긴다.
- 커밋 메시지는 `docs/development/commit_convention.md`를 따른다.

## 1차 목표: 데이터셋 영역 분리

이유:

- 다음 핵심 기능이 데이터 검수이기 때문이다.
- 현재 데이터 목록 렌더링, export, 저장 흐름이 `app.js`에 섞여 있다.
- 검수 상태, 수정, 삭제, 필터가 추가되면 `app.js`가 더 커진다.

작업 후보:

1. 데이터셋 생성 로직을 `src/features/dataset`으로 이동
2. JSONL export 로직을 `src/features/dataset`으로 이동
3. 데이터 목록 렌더링을 `src/ui`로 분리
4. 검수 상태 필드 추가
5. 검수 완료 데이터만 export

예상 커밋:

```txt
♻️ refactor: 데이터셋 로직 위치 정리

학습 데이터 생성과 JSONL 변환 로직을 dataset 기능 폴더로 분리함
```

## 2차 목표: 데이터 제작 탭 분리

이유:

- 질문, 핵심 사실, 말투 조건 입력 흐름은 채팅과 다른 목적을 가진다.
- 파인튜닝용 데이터 제작의 핵심 기능이므로 독립적으로 관리하는 편이 좋다.

작업 후보:

1. 초안 생성 요청 로직 분리
2. 최종 답변 저장 로직 분리
3. 입력값 검증 로직 분리
4. 제작 탭 렌더링 분리

## 3차 목표: 채팅 영역 분리

이유:

- 채팅은 실험용 대화와 좋은 답변 저장, 실패 기록을 함께 담당한다.
- 답변 저장 버튼이 데이터셋 기능과 연결되어 있어 경계가 흐려질 수 있다.

작업 후보:

1. 채팅 메시지 렌더링 분리
2. 좋은 답변 저장 액션 분리
3. 수정 저장 액션 분리
4. 실패 기록 액션 분리

## 4차 목표: 상태 관리 분리

이유:

- 현재 상태 변경이 여러 이벤트 핸들러에 흩어져 있다.
- 데이터 검수, 필터, 통계가 추가되면 상태 변경 규칙이 중요해진다.

작업 후보:

1. 기본 상태 정의 분리
2. 상태 저장 helper 정리
3. 프로필 업데이트 helper 정리
4. 데이터셋 업데이트 helper 정리

## 5차 목표: API 클라이언트 분리

이유:

- 브라우저에서 서버 `/api/chat`을 호출하는 코드가 채팅 흐름과 섞이면 제공자별 오류 처리가 어려워진다.

작업 후보:

1. `/api/chat` 호출 함수 분리
2. API 오류 메시지 정리
3. Ollama 연결 실패 안내 개선
4. OpenAI API 키 누락 안내 개선

## 보류할 것

- 대규모 프레임워크 도입
- 서버 DB 도입
- 폴더 구조에 맞춘 전체 파일 일괄 이동
- 테스트 자동화 없이 큰 구조 변경
