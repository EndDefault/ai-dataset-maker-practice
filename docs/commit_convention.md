# 커밋 메시지 규칙

이 프로젝트는 기능 단위로 작게 커밋한다. 커밋 메시지는 한국어로 작성하고, 제목만 봐도 무엇이 바뀌었는지 알 수 있게 쓴다.

## 기본 형식

```txt
이모지 타입: 40자 이하 제목

설명 1줄
```

예시:

```txt
✨ feat: 데이터 검수 상태 추가

학습 데이터 후보에 검수 전/완료 상태를 저장하도록 변경함
```

## 제목 규칙

- 제목은 40자 이하로 쓴다.
- 제목은 한국어로 쓴다.
- 제목 끝에 마침표를 붙이지 않는다.
- 한 커밋에는 한 가지 목적만 담는다.
- "수정", "작업", "변경"처럼 범위가 흐린 제목은 피한다.
- 무엇을 왜 바꿨는지 설명 1줄에 적는다.

## 타입 목록

| 이모지 | 타입 | 의미 |
| --- | --- | --- |
| ✨ | `feat` | 새 기능 추가 |
| 🐛 | `fix` | 버그 수정 |
| 📝 | `docs` | 문서 추가/수정 |
| 💄 | `style` | UI, CSS, 화면 스타일 수정 |
| ♻️ | `refactor` | 동작 변경 없는 코드 구조 개선 |
| ✅ | `test` | 테스트 추가/수정 |
| 🔧 | `chore` | 설정, 빌드, 기타 관리 작업 |
| 🗃️ | `data` | 데이터 모델, seed, export 구조 변경 |
| 🚧 | `wip` | 임시 작업 커밋 |

## 기능 단위 커밋 기준

좋은 커밋 단위:

- 데이터 검수 상태 필드 추가
- 데이터 항목 수정 UI 추가
- 검수 완료 데이터만 export
- README 실행 방법 보강
- Ollama 오류 메시지 개선

너무 큰 커밋:

- 데이터 관리 기능 전부 구현
- UI 전체 수정
- 문서 전체 정리와 기능 구현을 한 번에 처리

너무 작은 커밋:

- 오타 하나 수정
- 변수명 하나 변경
- 빈 줄 정리

단, 오타 수정이나 변수명 변경이 독립적으로 의미 있거나 다른 변경과 섞이면 위험할 때는 따로 커밋한다.

## 좋은 예시

```txt
✨ feat: 데이터 검수 토글 추가

저장된 학습 데이터 후보를 검수 완료로 표시할 수 있게 함
```

```txt
🗃️ data: 검수 상태 export 필터 적용

JSONL export 시 검수 완료 데이터만 포함하도록 변경함
```

```txt
🐛 fix: 빈 데이터 export 방지

저장된 학습 데이터가 없을 때 JSONL 다운로드가 실행되지 않게 함
```

```txt
📝 docs: 커밋 메시지 규칙 추가

기능 단위 커밋을 위한 제목 형식과 타입 목록을 정리함
```

```txt
💄 style: 데이터 카드 상태 배지 정리

검수 전/완료 상태가 데이터 목록에서 더 잘 보이도록 UI를 조정함
```

## 나쁜 예시

```txt
수정
```

이유: 무엇을 수정했는지 알 수 없다.

```txt
✨ feat: 이것저것 추가하고 오류 수정하고 문서도 고침
```

이유: 한 커밋에 여러 목적이 섞여 있다.

```txt
🐛 fix: 버그 수정
```

이유: 어떤 버그인지 알 수 없다.

## 커밋 전 확인

커밋하기 전에 다음을 확인한다.

- 변경 파일이 의도한 범위 안에 있는가?
- 기능 구현과 문서 수정이 필요 이상으로 섞이지 않았는가?
- 제목이 40자 이하인가?
- 설명 1줄이 변경 이유를 말하고 있는가?
- 테스트 또는 수동 확인 결과를 기록했는가?

## 이 프로젝트에서 추천하는 흐름

```txt
1. 기능 하나 구현
2. 관련 문서 갱신
3. 테스트 또는 수동 확인
4. git diff 확인
5. 기능 단위로 커밋
```
